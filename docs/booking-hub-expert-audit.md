# Экспертный аудит проекта Booking-Hub

Дата анализа: 2026-05-19

## 1) Executive Summary
Проект реализует базовый бизнес-процесс бронирования и уже имеет рабочие контуры backend/frontend, ролевую модель и Docker-сценарий запуска. При этом инженерная зрелость ограничена критическими разрывами в качестве поставки: автоматические тесты фактически не исполняются (`manage.py test` возвращает `Found 0 test(s)`), платежный контур имитирован и не защищает бизнес-операции от гонок/двойных действий, а прод-безопасность в `settings.py` почти не зафиксирована. CI/CD и базовые backup/restore есть, но эксплуатационная надежность и наблюдаемость остаются недостаточными для production-grade нагрузки. Проект можно довести до устойчивого состояния за 1-3 месяца при фокусе на P0-исправлениях.

Общая зрелость проекта: `Средняя`.

Интегральная оценка: `5.7/10`.

## 3) Ключевые проблемы (Top Issues)

- **[Severity: Critical] Тестовый контур не выполняется (ложное ощущение качества)**
  - Где проявляется: запуск `python manage.py test` в `backend/` возвращает `Found 0 test(s)`.
  - Почему это важно: любые регрессии проходят незамеченными; CI не дает гарантий качества релиза.
  - Подтверждение: фактический запуск в текущем окружении анализа показал `NO TESTS RAN`.

- **[Severity: High] Небезопасный и неидемпотентный платежный поток**
  - Где проявляется: `backend/apps/payments/views.py` (ручное изменение статусов оплаты/брони на GET/POST без провайдерской валидации вебхука и без защиты от повторных переходов).
  - Почему это важно: риск неконсистентных финансовых состояний, спорных операций и ошибок биллинга.
  - Подтверждение: `payment_success/payment_fail` меняют статус напрямую; `payment_pay` переводит бронь в `awaiting_confirmation` через имитационный сценарий.

- **[Severity: High] Недостаточная production-безопасность конфигурации**
  - Где проявляется: `backend/config/settings.py`.
  - Почему это важно: повышенный риск утечки данных, session hijack и неправильной экспозиции служебной информации.
  - Подтверждение: `DEBUG` по умолчанию `True`; отсутствуют явно заданные `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, HSTS-настройки.

- **[Severity: High] Возможные гонки при создании бронирований**
  - Где проявляется: `backend/apps/bookings/services.py` (`check_availability` + `create_booking` без `transaction.atomic`/блокировок на пересекающихся слотах).
  - Почему это важно: при конкурентных запросах возможно двойное бронирование одного интервала.
  - Подтверждение: нет использования `transaction.atomic`/`select_for_update` в критичном пути создания брони.

- **[Severity: Medium] Неполная эксплуатационная наблюдаемость**
  - Где проявляется: проект и CI/CD-контур.
  - Почему это важно: сложно обнаруживать деградации и быстро локализовывать инциденты в production.
  - Подтверждение: нет встроенных метрик/алертов/APM и регламентированного post-deploy smoke по бизнес-метрикам.

- **[Severity: Medium] Проблемы кодировки в документации/части контента**
  - Где проявляется: `README.md` и отдельные документы/строки при чтении.
  - Почему это важно: ухудшает поддерживаемость, вводит неоднозначности для команды и внешних участников.
  - Подтверждение: при чтении файлов фиксируются признаки mojibake.

## 4) Рекомендуемые корректировки

- **Восстановить корректное обнаружение и исполнение тестов (P0, M)**
  - Что изменить: привести тестовую структуру и discovery-настройки Django/CI к единому стандарту, зафиксировать обязательный прогон unit/integration в pipeline.
  - Почему это даст эффект: вернёт базовую гарантию качества и контроль регрессий.
  - Оценка усилий: `M`
  - Приоритет: `P0`
  - Ожидаемый результат: CI запускает и выполняет >80% целевых модульных тестов, `NO TESTS RAN` устранено полностью.

- **Перевести платежный контур на подтверждение от внешнего провайдера + идемпотентность (P0, L)**
  - Что изменить: внедрить callback/webhook валидацию, идемпотентные ключи/ограничения и строгую state-machine для оплаты/брони.
  - Почему это даст эффект: устранит ложные переходы статусов и финансовые расхождения.
  - Оценка усилий: `L`
  - Приоритет: `P0`
  - Ожидаемый результат: 0 неподтвержденных оплат в БД, повторные callbacks не меняют итоговое состояние.

- **Закрыть production security baseline (P0, S/M)**
  - Что изменить: жестко задать `DEBUG=False` вне dev, включить secure-cookie/HSTS/SSL-redirect, ревизию `ALLOWED_HOSTS`, секретов и env-практик.
  - Почему это даст эффект: снижает базовый вектор эксплуатационных уязвимостей.
  - Оценка усилий: `S/M`
  - Приоритет: `P0`
  - Ожидаемый результат: чек-лист OWASP ASVS L1 по конфигурации закрыт, security smoke проходит без критичных замечаний.

- **Сделать бронирование атомарным и конкурентно-безопасным (P0, M)**
  - Что изменить: обернуть создание брони в транзакцию, добавить блокировки/уникальные бизнес-ограничения на пересечения интервалов.
  - Почему это даст эффект: исключает двойные брони под нагрузкой.
  - Оценка усилий: `M`
  - Приоритет: `P0`
  - Ожидаемый результат: нагрузочный сценарий конкурентных запросов не создаёт конфликтующих броней.

- **Внедрить наблюдаемость и эксплуатационные SLO (P1, M)**
  - Что изменить: структурированные логи, базовые метрики (ошибки, latency, конверсия брони→оплаты), алерты и post-deploy smoke-runbook.
  - Почему это даст эффект: ускорит выявление инцидентов и снизит MTTR.
  - Оценка усилий: `M`
  - Приоритет: `P1`
  - Ожидаемый результат: MTTR снижен минимум на 30%, критичные ошибки обнаруживаются автоматически.

- **Нормализовать кодировки и документацию (P2, S)**
  - Что изменить: унифицировать UTF-8, пере-сохранить проблемные файлы, добавить линт/проверку кодировок в CI.
  - Почему это даст эффект: улучшит сопровождаемость и снизит риск ошибок коммуникации.
  - Оценка усилий: `S`
  - Приоритет: `P2`
  - Ожидаемый результат: 0 файлов с mojibake, документация читается консистентно во всех средах.

## 5) План внедрения по этапам

### Этап 1 (быстрые победы, 1-2 недели)
- Задачи:
  - Восстановить test discovery и обязательный прогон тестов в CI.
  - Ввести production security baseline в settings/env.
  - Добавить smoke-check после деплоя (health + критичные пользовательские сценарии).
- Зависимости:
  - Доступ к CI secrets и staging окружению.
- Риски:
  - Ложноположительные падения CI после включения строгих проверок.
- Критерии готовности:
  - CI стабильно запускает тесты; security baseline применён; smoke-check формализован и выполняется автоматически.

### Этап 2 (структурные улучшения, 2-6 недель)
- Задачи:
  - Реализовать корректный платежный workflow с внешним подтверждением.
  - Ввести атомарность и конкурентную защиту бронирований.
  - Добавить интеграционные тесты на status transitions и race conditions.
- Зависимости:
  - Выбранный платежный провайдер/контракт webhook.
- Риски:
  - Изменение бизнес-логики статусов потребует миграции текущих данных.
- Критерии готовности:
  - Финальные статусы платежей подтверждаются только провайдером; конкурентные тесты проходят без конфликтов.

### Этап 3 (долгосрочная эволюция, 1-3 месяца)
- Задачи:
  - Внедрить наблюдаемость (метрики, алерты, dashboard SLO).
  - Оптимизировать performance hotspots по фактическим метрикам.
  - Доработать эксплуатационную документацию и runbooks.
- Зависимости:
  - Выбор стека мониторинга и логирования.
- Риски:
  - Недостаточная дисциплина в сопровождении новых SLO/алертов.
- Критерии готовности:
  - Наблюдаемость покрывает основные бизнес-потоки; эксплуатационные процедуры воспроизводимы без «устных знаний».

## 6) Технический долг

- Что является техдолгом сейчас:
  - Неисполняемый тестовый контур.
  - Имитационный платежный процесс без подтверждения провайдера.
  - Недоформированная production security-конфигурация.
  - Отсутствие выраженной observability-платформы.

- Что можно отложить, а что нельзя:
  - Нельзя откладывать: test discovery/CI, безопасность конфигурации, атомарность бронирований, корректный платежный state flow.
  - Можно отложить (краткосрочно): расширенная аналитика/дашборды, косметическая реорганизация документации.

- Стоимость бездействия:
  - Рост числа скрытых регрессий и инцидентов.
  - Финансовые и репутационные риски из-за некорректных оплат/статусов.
  - Увеличение времени локализации проблем и стоимости каждой следующей доработки.

## 7) Check-list для повторной валидации

- [ ] `python manage.py test` запускает и выполняет тесты (не `0 tests`).
- [ ] CI блокирует merge при падении unit/integration тестов.
- [ ] В production `DEBUG=False`, включены secure cookie и SSL/HSTS-политики.
- [ ] Оплата фиксируется как успешная только после подтвержденного callback/webhook.
- [ ] Повторный callback или повторный запрос оплаты не меняет итоговый статус (идемпотентность).
- [ ] Конкурентные запросы на одинаковый слот не создают двойную бронь.
- [ ] Есть метрики и алерты на ошибки/латентность/конверсию брони в оплату.
- [ ] Документация и UI-строки читаются без проблем кодировки.

### Факты vs предположения

**Факты (подтверждены в ходе анализа):**
- В репозитории есть Django-приложения по доменам и workflow CI/CD.
- Локальный запуск тестов в `backend` возвращает `Found 0 test(s)`.
- Платежные статусные переходы реализованы приложением напрямую без подтверждения внешнего провайдера.
- В `settings.py` отсутствует часть production security baseline, `DEBUG` по умолчанию включён.

**Предположения (требуют подтверждения):**
- Реальная production-нагрузка и SLA проекта.
- Фактическая интеграция с платежным провайдером вне текущей ветки/репозитория.
- Наличие внешних систем мониторинга, не отраженных в кодовой базе.
